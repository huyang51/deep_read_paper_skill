# Phase 2 维度细则（11 维框架 · 单一来源）

> 本文是 SKILL.md Phase 2 的**细则唯一来源**：每个维度的提问清单、输出格式、硬性规则，以及类型路由调整表和两道跨维度硬检查（🌐 外部断言核验、📊 统计严谨性）都在这里。SKILL.md Phase 2 只保留总览与映射表；超长档编排派发任务卡时，把本文对应维度**整段粘贴**进【分析要求】槽位（见 orchestration_prompts.md 的单一来源原则）。

### 类型路由（Phase 0 判型，先判型再跑 11 维）

> **类型词表**（与速览卡 Category 一致）：**方法 / 理论 / 综述 / 基准 / 系统 / 报告**。判型依据 = 贡献列表第一条（主贡献）+ 章节骨架 + 图表类型，全在 Phase 0 分诊只读范围内完成。

**三条硬规则**：

1. **类型只改"每个维度问什么、拿什么当证据"，不减少维度数**。确定不适用于该类型的子项，在报告对应节写一行"本类型不适用（原因）"——禁止静默跳过（同"留白合法，编造样本违规"的纪律）。
2. **混合型按主贡献判型**，次贡献涉及的变化维度在该类型内加做；判不准 → 按"方法"跑全 11 维，报告元信息类型行标"（存疑）"。
3. **逐页全读与最高原则不受类型影响**：综述的 ELI5 是领域地图，理论的 ELI5 是证明直觉，方法的 ELI5 是直觉+数值示例——同等生效。

**类型 × 维度调整表**（只列发生变化的维度，未列出的照常执行；"§X 节名"指替换报告模板中该节标题）：

| 类型 | 识别信号（分诊可判） | 维度调整 |
|------|---------------------|---------|
| **方法**（默认） | 有"方法章 + 实验/消融表"，摘要给性能数字 | —（11 维照常，节名不换） |
| **理论** | 主体是定理/引理/证明；无训练流程；实验至多是验证性小规模 | 2.4 → **证明结构审计**（定理依赖链、每条假设的必要性、证明完整性、"证明略"清单、紧界还是存在性；**关键定理的证明步骤还原 ≤10 步**——逐条列出中间步骤，跳步处标注 [依据原文 Appendix 补全] 或 [报告补证]，>10 步的长证明还原主干、其余按依赖链分层概述）；消融 → **假设松弛分析**（放松某条件后结论如何退化）；2.7 → **定理条件外推**（假设不满足时会发生什么）；2.9 → **极限与退化情形**（样本量→∞/无噪声/分布退化）；§3 节名 → "理论结果与验证"；§3.7 统计台账 → 只审其**验证性实验**（无对照实验时写"本类型不适用（无对照实验）"，定理的"统计支撑"是证明，走 2.4 证明结构审计）。不适用：消融表、训练资源账本（无训练时）、超参可复现性 |
| **综述** | 无新方法；主体是分类体系+文献梳理；页数常 >30 | 2.1 → **领域脉络与分类轴**（用什么轴组织文献、轴是否 MECE、为什么是这几条轴）；2.2 → **谱系重建**（把分类改写成演化树，标出讲透与一笔带过的分支）；2.3 → 对象换成**领域全景**（术语体系+各方法共同骨架，取代伪代码/张量符号表/数值示例）；2.4 → **覆盖度审计**（检索式/收录标准/时间窗、明显该收未收的工作、分类是否穷尽）；2.6 → **相对已有综述的增量**；2.7 → **覆盖偏见与过时风险**；§2 节名 → "领域方法与谱系"、§3 → "覆盖度与分类审计"。不适用：消融分析、数值示例、资源账本、统计台账（均限"无自有实验"时——带原创实验/meta 分析的综述，其实验部分照跑并照常出台账） |
| **基准** | 贡献是数据集/评测集；有"构造流程+统计表+基线成绩表" | 2.2 → **与前代数据集的差异**（规模/领域/标注粒度/难度分布）；2.3 → **数据全流程**（采集→清洗→标注→划分，schema 与统计取代公式推导）；2.4 → **质量审计**（标注一致性、训练-测试泄漏、划分策略、指标定义、基线成绩的复现方式）；3.4 消融 → **规模与难度分层分析**；2.7 → **数据偏见、覆盖盲区、被刷榜风险**；§2 节名 → "数据构建"、§3 → "质量与评测审计"。不适用：张量符号表、模型伪代码（无新模型时） |
| **系统** | 贡献是工程系统/框架；有"架构+部署+吞吐/成本"章 | 2.2 → **工程前作差异**；2.3 → 数据流 + 成本账本（成本是主角）；2.4 → **系统评测审计**（吞吐/延迟/扩展性的测法是否公平、硬件是否对齐、与生产负载的差距）；2.7 → **失效模式与运维风险**；2.8 → **工程可复现与合规风险**；§2 节名 → "系统构建"、§3 → "系统评测"。不适用：张量符号表（除非核心优化公式需要推导） |
| **报告**（技术报告/白皮书，无同行评审） | 无 related work 定位章；大量工程细节与内部评测 | 2.2 → **技术脉络**（相对自家前代与同期竞品）；2.6 → **技术披露增量**（披露了多少别人可复现的细节）；2.8 → **可信度风险**（自评基准、选择性披露、无第三方验证；§4.7 节名同改）；§3.7 → **统计披露度**（盘有多少数字带方差/检验信息，作为 2.6 技术披露增量与 2.8 可信度风险的输入——无同行评审，不按投稿标准扣分）；§4.10 后验影响 → 重点看外部复现与质疑。不适用：投稿导向的表述分析 |

> ### 🌐 外部断言核验（跨维度硬性要求，主要约束 2.2 / 2.6 / 2.9）
>
> 模型对**当前论文之外**的文献记忆不可靠（编造"基座方法 X 提出了 Y"是最高频幻觉；标题相近的"戏仿论文"还会让纯记忆判断张冠李戴——本仓库实测翻出过两例）。因此：
>
> 1. **凡引用其他论文作为事实**——方法溯源（"基于 X 的 Y 机制"）、新颖性审计（"同期工作有 Z"）、反事实检验（"更强的基线 W"）——写入报告**之前**必须调用 MCP 工具 `cite_verify`（query=论文标题，带上断言声称的 author/year 做交叉核对）。
> 2. 按返回的 `verdict` 处理：
>    - `exact` / `probable` → 断言后标注核验出处：`[外部核验: <venue>, <year>, 被引 <N>]`
>    - `uncertain` / `not_found` → **禁止作为事实写入**。要么改写为论文原文确实支撑的表述，要么显式降级标注 `【未核验——仅模型记忆】`
>    - ⚠️ 特例（实战教训）：notes 含 `identifier unresolved`（常见于 arXiv 早期论文：OpenAlex 覆盖缺口 + S2 限流）时，`not_found` **不是反证**——按 DEFER 处理：换标识符（去作者重试/补 DOI）或稍后再试一轮；仍失败才降级【未核验】，且报告标注"外部库覆盖有限"
>    - `network_error` → 标注 `【外部核验不可用】`，流程继续，不得凭空补全
> 3. 论文发表满 1 年以上时，对**当前论文本身**调用 `paper_citations` 填写报告 §4.10"后验影响"（谁在引用、有无扩展/质疑迹象——只允许基于返回的施引工作标题/venue 陈述，**禁止**推断编造"复现失败"之类结论）。arXiv 论文优先传 `arxiv_id`；若返回解析失败提示（S2 限流），改用 `query=<论文完整标题>` 重试。
> 4. **报告点名的外部工作存在性门（§6 台账，报告定稿前跑一次）**：报告里**点名**的外部工作（基座方法、基线、同期工作、反事实里的"更强基线"）逐条列账，一条命令批量核验：
>    ```bash
>    python "<skill_dir>/tools/verify_refs.py" --refs "<清单文件>" --out "<vault>/reports/{short_name}_cite_ledger.json" --md "<vault>/reports/{short_name}_引用核验.md"
>    ```
>    清单每行 `标题 | 作者 | 年份 | doi:/arxiv:`（作者/年份**照论文参考文献原样填**——它们就是被交叉核对的字段；只给标题等于放弃错配检测）。产出 `cite_ledger.json`（机器可读）+ 可直接粘进报告 §6 的 Markdown 表；退出码 2 = 有行网络失败/待重试，重跑这些行。三态判定：**✅ 存在**（标题级命中且作者一致；年份不符就地注明——OpenAlex 合并版记录常标再索引年，不是错配证据）/ **⚠️ 疑似错配**（标题级候选里都没有自报作者——可能是标题形近的另一篇；报告展示分歧，不得静默采信任一方）/ **❓ 未收录**（外部库未覆盖，**不等于不存在**——禁止写成"不存在/伪造"，换标识符重试或标【未核验——仅模型记忆】）。

> ### 📊 统计严谨性硬检查（比较类数字断言的出口门，主要约束 2.4 / 2.9）
>
> 论文**自己报的数字**也有一条纪律：**"论文没报" ≠ "没做"，更 ≠ "结论错"**。本检查只做一件事——把"比较类断言"的统计支撑逐条盘清楚，缺口就地标 `[原文未交代]`，**禁止**把披露缺口推断成"未做检验→不可信"，也**禁止**编造"复现失败/不显著"之类反向结论（与"未收录 ≠ 不存在"同源）。
>
> 1. **触发**：报告里每一条**比较类数字断言**（A 比 B 高/优/提升 X——含主结果、消融增量、效率对比、分层/切片分析）都要进 §3.7 台账。只有定性说法而无数字的声明不进台账，但要在 2.4 的"声明-证据对照"表里明确指出"该声明无数字支撑"。
> 2. **台账四问**（逐条答，论文没写就写 `[原文未交代]`，不许留空、不许替它猜）：
>    - **重复性**：跑了几次/几个种子？报的是单次、best-of-k，还是 mean±std？（只报单次 = 波动未知）
>    - **显著性**：有无检验（paired bootstrap / t-test / Wilcoxon / McNemar）与 p 值或置信区间？**检验单元**是 query/样本还是数据集？（对 n=5 的数据集做 t 检验 = 不具推断力，就地标注这一事实）
>    - **幅度 vs 波动**：Δ 是否超过已报的 std/置信区间？论文未报波动时**不得替它宣称"显著"**，只能写"波动未知，Δ 与常见波动同量级"这类有据表述。
>    - **选择空间**：这条断言是从多少个指标 × 数据集 × 基线 × checkpoint 里挑出来的最优？（选择空间大 = 多重比较风险，标注风险来源，**不代替作者下结论**）
> 3. **红线**：`[原文未交代]` 是**披露缺口**标注，不是扣分项、更不是造假证据。数字本身仍按三态标注如实转写（明述/推断/重构）——统计台账管"有没有统计支撑"，事实核验管"数字对不对"，两条线不得互相冒充。
> 4. **类型路由**：变化见『类型 × 维度调整表』各行的 §3.7 项；确认不适用时在 §3.7 写一行"本类型不适用（原因）"，禁止静默跳过。

### 2.1 问题溯源分析

回答以下问题：
- **作者发现了什么问题？** 描述具体的研究痛点或现有方法的缺陷
- **为什么这个问题重要？** 解决它能带来什么价值
- **前人为什么没能解决？** 现有的方法卡在哪里（性能瓶颈、假设过强、数据稀缺等）
- **作者的分析思路是什么？** 他们通过什么观察/实验发现了问题的突破口
  - ⚠️ **思维链证据规则（硬性）**：论文对发现过程的交代多为事后重构叙事。"诊断观察 → 关键 insight → 方法转化"每一环必须按报告 §1.4 规则标注出处（`[原文 §X 明述]` / `[据…推断]` / `[重构——原文未交代]`）；原文没写的环节**留白写明没写**，禁止编一个合理化的发现故事把链条抹平

### 2.2 方法溯源分析

这是最关键的分析维度。需要回答：
- **方法是原创的还是基于前人改进的？** 如果是原创，原创性体现在哪里。如果是改进，需要明确画出改进脉络
- **改进的基座是什么方法？** 列出具体的论文和对应的方法名
- **改进思路是什么？** 描述从基座方法到本文方法的变化链条：
  - 基座方法做了什么假设/设计？本文如何改变这些假设/设计？
  - 改变背后的动机是什么（解决基座方法的哪个缺陷）？
  - 这种改变的技术难度在哪里？
- **与其他同期方法的对比定位**：在相关工作中，本文方法处于什么位置

以上分析需要写成连贯的叙述，而不是问答列表。同时提供一个**改进脉络对比表**，让读者一目了然：

| 维度 | 基座方法 A | 基座方法 B | **本文方法** |
|------|-----------|-----------|-------------|
| 核心设计 | ... | ... | ... |
| 本文借鉴了什么 | ... | ... | — |
| 本文改变了什么 | — | — | ... |

格式示例：

> 作者在分析 [基座方法] 时发现，该方法在 [具体场景] 下存在 [具体问题]，其根本原因是 [深层分析]。为解决这一问题，作者借鉴了 [相关工作] 中的 [核心技术思想]，但做了 [关键改动]，从而 [改进效果]。与之同期，[另一方法] 也试图解决类似问题，但采用了 [不同思路]，本文的方法与之相比 [优势/差异]。

### 2.3 方法通俗解读

对于论文提出的方法，用通俗易懂的语言进行解读。**按报告模板的组织顺序**：先直觉（报告 §2.1）→ 全景（报告 §2.2）→ 溯源（报告 §2.3）→ 细节（报告 §2.4-2.7），让读者在知道方法"是什么"之后再追问"从哪来"。

- **核心直觉**：先用一句话/一个类比解释方法的核心思想（就像向非专业人士解释）。这是读者建立心理模型的入口，应放在所有方法细节之前
- **方法全流程概览**：按执行顺序完整叙述方法的全部流程（输入 → 各阶段/组件 → 输出），用连贯的叙述性语言让读者获得方法的"森林视图"。覆盖所有主要组件，标注图表/算法编号以追溯原文。**在每个阶段末尾标注对应的关键公式编号**（如"→ 详见公式 3"），让读者知道该阶段的核心数学在报告 §2.6 节中何处展开，但不在此展开公式细节
- **输入输出规格**：详细说明方法各模块的输入输出，让读者能真正复现数据流：
  - 输入是什么？（如：文本 token 序列、图像 patch、特征向量等）
  - 输出是什么？（如：分类 logits、embedding 向量、生成文本等）
  - 每一步的张量形状/维度变化（如：输入 `[B, L, D_in]` → 编码后 `[B, L, D_out]`）
  - **⚠️ 形状符号必须显式定义**（强制项）：在输入输出规格表前，**必须**先列一张「张量符号约定表」，把表格中出现的 $B$、$L$、$D$、$H$、$W$、$C$、$k$、$\bar{d}$ 等所有符号一次性解释清楚（含本方法中的具体取值），**禁止**让读者自己去猜符号含义
  - 关键中间表示的形式和含义（如：attention map `[B, H, L, L]`）
  - 如果有多个模态/分支，分别说明各自的数据流
- **方法结构**：描述整体模型/算法架构，可以用分层的"模块图"来描述数据流动，配合输入输出规格说明数据在各模块间的流转
- **图文结合（硬性）**：方法叙述必须配合 1.3 提取的原图——总览图嵌入报告"核心图速览"与 §2.2，模块级细节图嵌入 §2.4；讲每个阶段时点名图的对应区块（"即 Figure 1 左侧的 Encoder 堆叠"）。**只存在于图中的信息**（连线方向、跳连/残差路径、分支汇合点、图内维度小字）必须读图后在文字中显式补出，禁止只凭正文推断图的内容
- **端到端示例走通**：用一个具体的、可追踪的实例走通从输入到输出的完整流程。示例要具体到数值（如 attention weights = [0.1, 0.05, 0.6, ...]），用逐步追踪表记录每一步的数据变化，并关联到全流程概览中的各阶段编号。抽象的张量形状不如一个具体例子有说服力
- **关键公式解读**：对每个关键公式，分别给出：
  - **标注所属阶段**：先指明该公式用于全流程概览中的哪个阶段（引用阶段编号），让读者将公式与全景流程对应
  - 公式的整体含义（一句话概括）
  - 每个变量的含义和物理/数学意义
  - 公式各部分的作用（如损失函数中各项的约束目标）
  - 为什么这样设计（而不用其他形式）
- **训练/推理流程**：描述方法在实际使用时的流程。训练：输入→前向各阶段→损失计算→反向，标注每步数据形状、哪些参数冻结/可训练。推理：完整推理链路。如论文提供了计算效率数据（推理延迟、吞吐量、token 数等），与 baseline 对比列出
- **基础知识地图**（写入报告"📚 基础知识地图"节）：本文依赖的前置概念 ≤8 个，每个给"一句话定义 + 在本文何处用到（精确到章节/公式） + 需要懂多深"。这一节决定基础薄弱的读者能否独立读懂报告——是 ELI5 原则的前置支撑，不是术语表罗列
- **双层讲解（原则）**：通俗解读（§2.1-2.2 比喻与全景）与深入讲解（§2.8 完整伪代码、复杂度分析、数值稳定性细节、边界情形）缺一不可——"通俗版是入口，不是终点"。深入讲解允许使用 §2.4-2.7 已解释的符号，但每节仍须自足；论文没交代的数值细节写"未交代"，不许猜

### 2.4 实验设计分析

分析实验设计的逻辑：

- **声明-证据对照**（关键！）：列出论文的核心声明（通常在引言末尾或摘要中），逐一对照实验章节检查每个声明是否有对应的实验支撑。如果某个声明缺少实验验证，明确指出。格式如下：

  | 论文声明 | 支撑实验 | 是否充分 | 说明 |
  |----------|----------|----------|------|
  | "方法 X 在 Y 任务上超越 SOTA" | Table 1 | 充分 | 多数据集、多基线验证 |
  | "模块 A 对性能至关重要" | Table 3 消融 | 充分 | ... |
  | ... | ... | ... | ... |

- **每个实验的证明目标**：作者设计的每个实验分别想证明什么
- **实验设计的合理性**：这些实验是否能充分验证论文的声明？有没有缺失的验证维度？
- **数据集深析（硬性）**：训练/评测的每个数据集产出一张卡片（任务与格式/规模与划分/内容与标注/已知问题）+ **一条样本示例**——让读者直观看到"一条数据长什么样"。样本来源三选一并标注：`[原文示例转写]` / `[公开数据集通行示例——未对原数据核验]` / 给不出时明写"无法给出样本"。**留白合法，编造样本违规**。公开数据集的示例按官方 schema 复现，禁止冒充真实抽到的样本
- **基线选择（升格为逐条深析）**：每个 baseline 给"流派一句话定位（cite_verify 出处）+ 为什么被选（覆盖哪个对比维度）+ 对比公平性（数据/调参预算/评测协议是否对等）"；表后必答"**缺席的强基线**"——按当前认知该比而没比的是谁、缺席影响哪个结论的可信度（该断言本身也过 cite_verify），与反事实检验衔接
- **关键实验结果的解读**：哪些数字最关键？它们说明了什么？
- **曲线/定性图同样是实验（硬性）**：趋势、效率、scaling、失败案例类结论往往由结果图而非表格支撑——嵌原图并基于亲眼看图解读：写明坐标轴含义与单位、有无误差线、曲线趋势与正文 claim 是否一致；**图文不一致处必须显式标记 ⚠️**（如正文称"稳定提升"但曲线有大幅震荡/部分区间被基线反超）
- **消融实验深度分析**（关键！不只是复述消融表）：消融实验是理解"方法为什么有效"的最直接窗口。深入回答：
  - 每个消融项的性能变化说明了什么？哪个组件/设计选择对性能影响最大？
  - 有没有反直觉的结果？（如"加了 X 反而变差"、"去掉看似重要的 Y 却没有明显下降"、"两个独立有效的模块组合后反而效果下降"）
  - 哪些设计是冗余的、可以简化或移除而不影响性能？（这对实际部署有直接指导意义）
- **⚙️ 训练资源账本**（写入报告 §2.7 资源账本块）：参数量/数据量/硬件卡时/精度优化器策略/总 FLOPs，逐项记录论文交代值并给出处；**论文未交代时必须做数量级估算**——FLOPs≈6×N参数×Ntokens、卡时=FLOPs/(峰值×MFU 25~50%)、显存≈参数×16-18B+激活——写成区间并标 `[估算——重构，原文未交代]`，禁止伪装精确
- **可复现性评估**：论文是否提供了代码？关键超参数是否完整？训练细节是否充分？是否有未说明的实现技巧可能影响复现？训练资源是否交代（未交代→用上面"资源账本"的估算工具箱给数量级区间）；把"复现还缺什么信息"列成缺口清单，与 §2.8 深入讲解的"未交代"项互相印证
- **📊 统计严谨性台账（硬性，写入报告 §3.7）**：逐条盘比较类数字断言的统计支撑（重复性/显著性/Δ vs 波动/选择空间四问），规则见上方"📊 统计严谨性硬检查"块——缺口标 `[原文未交代]`，不得推断"不显著/不可信"

### 2.5 局限性分析

诚实分析论文的局限：

- **方法局限**：方法的适用范围、假设条件、计算开销等
- **实验局限**：未覆盖的场景、数据集偏差、评估指标的盲区
- **理论局限**：是否有理论保证？如果有，理论假设是否合理
- **作者是否诚实**：论文的 limitation/讨论部分是否诚实讨论了这些问题
  - **沉默对照清单（硬性产出）**：本维度每条发现（方法/实验/理论局限）逐一与作者自述对账，标 ✅已述（含提及深度：一句话带过/展开分析）/ ⚠️变相提及（包装进"未来工作"）/ ❌未提及。❌ 行逐条给"为什么作者应当讨论而没讨论"——依据只允许论文内部证据（实验设计、附录、措辞对比），不得把"没写"直接断言为"心虚"
- **可能的改进方向**：基于以上分析，提出 2-3 个切实可行的改进方向

> 以下三个维度（2.6 / 2.7 / 2.8）是**审稿人视角**的批判性分析，区别于前 5 个维度的"理解论文"立场。这三节共同回答"这篇论文是否值得发表"，与 2.5 局限性分析构成"作者自评 → 读者深挖 → 审稿人判断"的递进链。

### 2.6 新颖性审计（审稿人视角）

回答的核心问题：这篇论文相对已有工作的**创新增量**是多少？是范式转变还是 trick 堆叠？读者读完本节后应能回答"我是否应该花 3 小时精读这篇论文"。

> 与 2.3 方法溯源分析的区别：2.3 是**事实陈述**（作者从哪个基座改了什么），2.6 是**价值评判**（这个改动值不值得）。

需要回答：

- **创新增量定级**：按以下三档对论文评级，每档给出 1-2 句判定理由
  - **Incremental（边际改进）**：换了 backbone、加了正则、调了 loss 等常规工程改进
  - **Substantial（重要改进）**：新架构组件、新训练范式、对核心问题有新解法
  - **Breakthrough（范式转变）**：开辟新问题、新范式或显著刷新领域认知
- **声称-实质对照**：列出摘要/引言中的 3-5 条核心声称，逐一检查方法/实验是否真有对应实现，识别"overselling"（如：声称"理论保证"但无证明、声称"广泛适用"但只测了一个数据集）
- **与同期工作的边界**：该方向近 1-2 年有哪些并行工作？本文方法与之相比，差异是"实质"还是"包装"（换 backbone / 换数据集 / 改评测指标等）？
- **学术脉络定位**：在该问题方向的发展树中，本文属于"开创性 / 扩展性 / 边缘性"中的哪一类？

### 2.7 失败案例与边界条件（审稿人视角）

回答的核心问题：方法在哪些场景**真的会失效**？这是审稿人高频追问的实验类型。

> 与 2.5.2 实验局限的区别：2.5.2 是作者**主动承认**的盲区（数据集偏差、指标盲区）；本节是读者**主动挖掘**的失效场景——通常作者不会主动展示，但审稿人会要求补。

需要回答：

- **核心假设清单（编号 M1…Mn）**：列出方法依赖的 3-5 个**方法/算法内部**假设（如"输入服从高斯分布"、"query 与 doc 长度匹配"、"打分函数可加性"），逐一分析在什么实际场景下会破。**只收方法内部假设**——数据/评估/工程/用户类假设归 2.10 的 A 表，不在本表重复（见下方归属判定）；§4.6.2 每个失效场景以 `M编号` 开头标出来源
- **推断的失效场景**：基于假设清单，推测 3-5 个**作者未在文中展示的**失效场景，每个说明三要素：触发条件 / 预期失效表现 / 可观察的征兆（如：训练时 loss 波动剧烈 / 推理时输出退化 / 跨域时性能骤降），并以 `M编号` 标出源自哪条假设（§4.6.2 表不加列，编号写在"场景"格里——§4.5-4.9 表格列数 ≤4 的排版硬规）
- **跨域/跨尺度泛化空白**：方法在哪些领域/规模/分布上**没有验证**？这些空白是否构成显著风险？例如：只在英文数据上验证 → 中文场景是否有效？只在 224×224 验证 → 高分辨率是否崩溃？
- **抗干扰鲁棒性**：对输入扰动（噪声、对抗样本、分布偏移）的鲁棒性是否验证？这是审稿人高频追问点

### 2.8 拒稿风险评估（审稿人视角）

回答的核心问题：综合前面所有维度，**如果审稿人想拒稿**，理由会是什么？

> **这不是"给出拒稿结论"，而是"列出可能触发拒稿的标准依据"**。一篇论文即使整体不错，审稿人也需要识别其"最薄弱环节"。这一节让读者学会用审稿人的标准审视论文——既提升自己的写作水平，也帮助写 rebuttal。

需要回答：

- **拒稿标准清单对照**：按 ICLR/NeurIPS 等会议常见的拒稿理由类型（最多 8 类：增量贡献不显著 / 实验不充分 / baseline 不公平 / 表述不清 / 理论错误 / 复现性差 / 范围过窄 / 伦理问题），逐项对照本文实际情况，用 ✅/⚠️/❌ 标注
- **潜在拒稿理由 (Top 3)**：按严重度排序，列出最可能触发拒稿的 3 条理由，每条包含三要素：
  - **触发证据**：来自前 2.6 / 2.7 章的具体事实
  - **严重度**：高（致命）/ 中（重要但可补救）/ 低（小瑕疵）
  - **Rebuttal 补救方案**：作者可在 rebuttal 阶段补充的实验或论证
- **整体风险等级**：综合 Top 3 理由，给出三档定性评级：**高风险拒稿** / **中等风险（需 rebuttal）** / **低风险**。注意：这一评级反映"拒稿风险"，不代表论文的真实价值。

### 2.9 关键论断的反事实检验（深度理解）

回答的核心问题：论文的每条核心论断，**在什么条件下会被推翻**？这是审稿人和一流读者的分水岭——一流读者不光看作者怎么论证 X 成立，还主动构造 X **不成立**的反例。

> 与 2.4 实验设计的区别：2.4 是**正向**核对（声明-证据映射，确认作者论证了什么），2.9 是**反向**思辨（主动构造反例，检验论断的鲁棒性）。

需要回答：

- **核心论断清单**：从摘要 / 引言末尾 / 结论中提取 3-5 条**最核心**的论断（不是所有声明，是支撑全文的"支柱论断"）
- **推翻条件 (Falsification Conditions)**：对每条论断，写出"什么条件下这条论断会站不住脚"。至少包含三类反例：
  - **数据替换**：换数据集 / 换 domain / 换分布偏移下，论断是否还成立？
  - **规模缩放**：把模型 / 数据 / 训练时长 scale up 或 down 10×，论断是否还成立？
  - **基线增强**：给 baseline 同等调优 / 算力 / 工程优化后，差距是否消失？
- **鲁棒性评级**：对每条论断，按"反例容易构造的程度"打分：
  - **🔴 脆弱**：只要稍微改变条件（如换 backbone / 加正则）就垮掉
  - **🟡 中等**：需要构造特定反例才垮，但反例合理
  - **🟢 鲁棒**：很难构造反例，论断在大多数条件下成立

> **写作示例**：
>
> > 论断："我们的方法在 MS MARCO 上比 BERT-large 高 2.5%"。
> > 推翻条件：若 (a) 用 ColBERTv2 替换 BERT-large 作 baseline；(b) 用真实查询而非 MS MARCO 公开 query；(c) 给 baseline 同等 query augmentation 超参搜索预算——2.5% 差距可能消失。
> > 鲁棒性评级：🟡 中等。

### 2.10 隐含假设审计（深度理解）

回答的核心问题：论文有哪些**没说但默认成立**的关键假设？这些假设如果不成立，结论还成立吗？

> 与 2.5 局限性分析的区别：2.5 是作者**主动承认**的局限（论文 limitation 章节）；2.10 是读者**主动挖掘**的"作者没明说但读者必须知道"的隐含假设——通常作者不会主动声明，因为这是他们"想当然"的领域常识。

需要回答：

- **隐含假设清单（编号 A1…An，跨三个类别连续编号）**：列出 3-5 个论文**未明说但默认成立**的假设，典型类别：
  - **数据假设**：训练-测试分布是否一致？是否存在数据泄露？长尾是否覆盖？
  - **评估假设**：评测指标是否合理？评测脚本是自己的还是 baseline 作者的？评测用的 checkpoint 是 best 还是 last？
  - **工程假设**：baseline 是否同等调优？训练时长 / 算力是否对齐？超参搜索空间是否对等？
  - **用户假设**：真实用户行为是否与测试 query 分布一致？

> **与 2.7 的归属判定与去重硬规则（两张假设表互斥且完备）**：一条假设只进一张表——**归属判定问一句"假设破了以后，是方法失真还是证据失效？"**前者进 2.7 的 M 表（喂失效场景），后者进本表 A 表（喂风险图与可信度评级）。两栖情形（如"训练-测试分布一致"既让方法退化又让数字失真）按**主要杀伤**归 A 表，若确属方法机理前提则在 M 表留一行 `见 A2`，**禁止两处各写一遍**——这正是本节与 §4.6.1 曾经的重复病灶。定稿前逐条对核 M 表 × A 表：条目不得重复、跨表互引编号必须有效。（超长档下 §4.6.1 出自任务卡 B、§4.9.1 出自任务卡 C，装配时按"六对张力"第 5 项核对。）
- **作者验证情况**：对每个假设，标注作者**是否主动验证**：
  - ✅ **已验证**：作者在论文中给出实验证据
  - ⚠️ **部分验证**：作者提及但未充分展开
  - ❌ **未验证**：作者完全未提及，读者需要警惕
- **风险评级**：未验证的隐含假设是否构成结论可信度的显著风险？高/中/低三档

> **为什么这一节重要**：许多论文被推翻不是方法本身有问题，而是**评测条件不公平**或**baseline 调优不充分**。隐含假设审计是识别这类"软性 trick"的关键工具。

### 2.11 综合判断（深度理解，必填）

回答的核心问题：在完成 §4.1-4.10 的所有"判定"后，**给读者一个能直接指导下一步研究的"行动地图"**。

> 与 §4.5-4.10 的区别：§4.5-4.10 是分散的"判定清单"，本节是**把所有判定汇总为可操作的结论**。读者读完本节应能回答"如果我要在这篇工作基础上做下一步研究，我该从哪个角度切入"。

需要回答：

- **方法层面**：哪些方法假设最可能不成立？最该补的 ablation 是什么？
- **实验层面**：数据集偏差在哪？最该补的 baseline 是什么？
- **评估层面**：评测指标有哪些盲区？可复现性风险有多大？
- **应用层面**（可选）：部署到真实场景的最主要障碍是什么？
- **整体定位**（可选）：这篇论文在领域中的位置？对后续工作的启发是什么？

> **写作要求**：用 3-5 段**连贯叙述**回答以上问题，**禁止**以"高/中/低"标签结束全节。每段 80-150 字。
